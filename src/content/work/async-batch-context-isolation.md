## 핵심 변경

비동기 작업마다 독립적인 Map과 식별자를 생성하도록 변경했습니다. 테스트 코드를 작성한 기록과 실제 테스트 실행 결과를 구분하며, 운영에서 보고된 DB 예외와의 직접적 인과는 별도 확인 대상으로 남깁니다.

## 관찰된 문제

여러 시험을 동시에 일괄(배치) 실행하는 과정에서 실행 이력 테이블 insert 시 기본키 중복 예외(`DuplicateKeyException`)가 반복 발생하는 문제가 보고되었습니다.

작업 기록에는 PK 중복으로 추정했다는 내용이 남아 있습니다. 관련 코드에서는 실행 요청 파라미터가 비동기 태스크 간에 섞일 수 있는 결함이 확인됐습니다. 조사 가설의 정확한 시간 순서는 자료로 복원할 수 없습니다.

## 코드에서 확인한 결함

배치 실행 로직을 검토한 결과, 반복 루프 외부에서 생성된 단일 `Map` 객체가 루프 내의 모든 비동기 실행으로 전달되고 있었습니다.

각 iteration에서는 동일한 맵 참조(Reference)에 대해 `requestId`와 `instanceId`를 덮어쓴 뒤 비동기 실행자(async executor)에 넘겨주고 있었습니다. 비동기 스레드가 실제 파라미터를 읽는 시점에는 이미 후속 루프의 값으로 덮어써졌을 가능성이 높았고, 이로 인해 이전 호출이 엉뚱한 식별자를 참조하거나 실행 컨텍스트가 오염되는 데이터 레이스가 코드상에 명확히 존재했습니다.

## 변경

각 비동기 호출 단위의 실행 컨텍스트를 분리하는 변경을 적용했습니다. 락이나 동기화 방식과 상세 비교를 수행했다는 당시 기록은 확보되지 않았습니다.

- 반복 루프마다 새로운 `HashMap` 인스턴스를 생성하여 비동기 작업에 전달
- 각 실행 호출마다 독립적인 UUID와 인스턴스 식별자를 부여
- 빈 인스턴스 목록이 들어올 경우 불필요한 비동기 작업이 기동되지 않도록 방어 로직 추가

이로써 비동기 스레드 간의 참조 공유로 인한 부수 효과를 제거하고, 각 작업이 온전히 독립된 요청 상태를 유지하도록 구성했습니다.

## 검증 가능한 것

상세 복원 자료에는 다음 조건을 다루는 신규 테스트 코드가 기록돼 있습니다.

- **인스턴스별 독립 Map 참조 전달**: 각 비동기 호출이 서로 다른 맵 인스턴스를 수신하는지 검증
- **식별자 고유성**: 각 호출에 고유한 `requestId`와 해당 iteration의 올바른 `instanceId`가 바인딩되는지 확인
- **경계 조건**: 빈 작업 목록 입력 시 비동기 태스크가 호출되지 않는 흐름 확인

테스트 코드의 존재는 검증 의도를 보여줍니다. 당시 실행 로그와 CI 결과가 없어 테스트 통과나 운영 회귀 방지 완료로 표현하지 않습니다.

## 아직 확정할 수 없는 것

- **DB PK 충돌과의 직접적 인과**: 공유 Map 재사용과 독립 컨텍스트로의 변경은 코드 복원 자료에 남아 있습니다. 이 결함이 운영에서 발생한 `DuplicateKeyException`의 유일한 원인이었는지는 프로덕션 트레이스 로그가 없어 확정하지 않습니다.
- **운영 배포 후 재발 방지 여부**: 코드 반영 이후 CI 빌드 통과 로그나 실제 배포 후의 장기적인 오류 재발률, 정량적인 장애 감소 수치는 확보된 자료만으로는 단정할 수 없으며 불확실성으로 남겨둡니다.
