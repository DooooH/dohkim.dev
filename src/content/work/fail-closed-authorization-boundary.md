## 빠져 있던 권한 경계

시스템 초기 개발 과정에서는 권한 제어가 프론트엔드 UI 수준의 메뉴 노출 여부에 치우쳐 있어, 백엔드 리소스 레벨의 인가 경계가 충분히 갖춰지지 않은 상태였습니다.

비관리자가 endpoint와 리소스 식별자(ID)를 알고 직접 API를 호출할 경우, 자신에게 할당되지 않은 타 브랜드나 타 지역의 데이터에 접근할 수 있는 경로가 존재했습니다. 구체적으로 상세 조회(detail), 초기화(reset), 다운로드(download), 삭제(delete) 등의 동작에서 브랜드 및 지역에 대한 리소스 수준 검증(resource-level validation)이 누락되어 있었고, 대시보드 실시간 집계 쿼리에도 관리자 및 테넌트 조건 파라미터 필터가 빠져 있었습니다.

## 정책 결정

운영 중인 백오피스 업무 연속성을 해치지 않으면서도 비인가 접근 가능성을 차단하기 위해 다음과 같은 정책 기준을 수립했습니다.

- **기존 관리자 전역 조회 유지**: 시스템 관리자는 브랜드나 지역 제약 없이 전체 데이터를 조회할 수 있도록 기존 admin 권한 체계를 유지했습니다.
- **비관리자의 명시적 scope 제한**: 비관리자 요청에 대해서는 백엔드에서 인가된 brand/region scope를 엄격히 검증하여 할당된 범주 내의 데이터만 허용하도록 제한했습니다.
- **모호한 권한의 Fail-Closed 처리**: 요청자의 권한 scope가 비어 있거나(blank) 해석이 모호한 경우, 임의로 허용하지 않고 즉시 차단(fail-closed)하거나 0건으로 처리하도록 규칙을 명확히 했습니다.
- **리소스 식별자 열거 완화**: 존재하지 않는 ID(missing ID)와 권한이 없는 ID(unauthorized ID)에 대해 서로 다른 에러나 상태를 노출하지 않고 동일한 응답으로 처리하여, ID 추측을 통한 리소스 탐색을 방지했습니다.

## 코드 적용 범위

프론트엔드 응답 규약을 깨뜨리지 않고 백엔드 컨트롤러, 서비스, 매퍼, SQL 쿼리 전반에 걸쳐 일관된 권한 검증을 반영했습니다.

- **단건 리소스 검증**: 상세 조회, 리셋, 다운로드, 파일 삭제 등 주요 endpoint 진입부 및 서비스 계층에서 대상 리소스의 브랜드/지역 scope 유효성 검사 적용
- **다건(Bulk) 처리 시 인가 ID 선별**: 일괄 처리 요청 시 요청자가 접근 가능한 리소스 ID만 선별하여 안전하게 로직을 수행하도록 변경
- **대시보드 쿼리 스코프 필터링**: 실시간 통계 및 집계 SQL에 관리자 여부와 인가된 테넌트 범위를 조건문으로 주입해 비관리자 조회 시 권한 외 데이터가 합산되지 않도록 보완

## 검증 범위와 한계

- **접근 가능 조건 제한 확인**: 백엔드 계층에서 scope 검증과 SQL 필터링이 누락 없이 동작하도록 구현하여, 비인가자가 ID 직접 호출을 통해 권한 밖 리소스에 접근할 수 있었던 조건을 코드 수준에서 제한했습니다.
- **불확실성 및 남은 한계**: 실제 운영 환경에서 본 결함으로 인한 정보 유출 사고나 악용 사례가 발생했는지는 확인된 바 없습니다. 또한 전체 시스템을 아우르는 E2E 권한 자동화 테스트 완료 여부나 운영 access log 기반의 전수 검증 결과는 확보된 자료에 없으므로 불확실성으로 남겨둡니다.
