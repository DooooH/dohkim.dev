## 문제: 수집 주기는 200ms인데 그래프는 비어 있었다

운영 포털에서 서버의 throttling 관련 메트릭을 실시간에 가깝게 보여주기 위해, 메트릭 수집 주기를 최소 200ms까지 낮출 수 있는 파이프라인을 구성했습니다. 여기서 중요한 요구사항은 항상 200ms로 수집하는 것이 아니라, 필요할 때 200ms 수준까지 조정할 수 있어야 한다는 것이었습니다.

그런데 개발 중 수집 주기를 200ms로 설정해도 화면에는 한 초 안에 기대한 만큼의 데이터가 보이지 않았습니다. 어떤 초에는 데이터가 하나뿐이었고, 어떤 초에는 아예 점이 없었습니다. 포털은 비어 있는 구간을 앞뒤 점으로 연결했기 때문에, 실제로는 관측값이 없는 구간이 긴 직선처럼 표시되었습니다.

문제의 핵심은 설정 파일에 `200ms`가 들어 있는지가 아니었습니다. 메트릭이 만들어진 뒤 수신 API에 도착하고, validation을 통과해 저장되기까지 실제로 얼마나 걸리는지를 확인해야 했습니다.

<Callout type="note" title="이 글에서 말하는 200ms">
  200ms는 수집 주기를 낮출 수 있어야 한다는 요구사항이자 end-to-end latency를 판단할 때 사용한
  목표입니다. 수집 주기, Telegraf가 output을 flush하는 주기, API에 도착하는 시간은 서로 다른
  값입니다.
</Callout>

## 파이프라인의 각 경계를 먼저 그렸다

Telegraf가 수집한 데이터를 REST API로 바로 보내는 대신 Python sender를 중간에 두었습니다. 여러 메트릭을 같은 timestamp 기준으로 묶고, API에 전달하기 전에 일부 필드를 가공해야 했기 때문입니다. 당시 사용하던 Telegraf 기능만으로 이 변환을 구성하는 것보다, Python 계층에 데이터 변환 책임을 두는 편이 구현과 유지보수 측면에서 다루기 쉬웠습니다.

초기 구조는 다음과 같습니다.

<Mermaid chart={initialFlow} label="Initial metric delivery flow">
  <span slot="caption">
    수집, 전송, validation, 저장을 하나의 지연으로 보지 않고 경계별로 나눠 관찰했습니다.
  </span>
</Mermaid>

이 구조를 분석할 때는 각 단계에서 timestamp가 언제 생성되는지와 어느 시점에 데이터가 묶이는지를 구분해야 합니다. 특히 `collection interval`이 짧아도 Telegraf 내부에서 output flush를 기다리거나, Python interpreter를 새로 시작하는 시간이 추가될 수 있습니다.

### 수신 API의 validation이 누락을 드러냈다

수신 API는 metric timestamp와 서버 수신 시각의 차이를 검사하고 있었습니다. 지나치게 오래된 값이 뒤늦게 도착하면 현재 상태를 설명하기 어렵고, 수집 경로에 문제가 생겼을 때 stale data를 그대로 저장하지 않기 위한 방어선입니다.

그래프에서 누락을 확인한 뒤 API 수신 로그를 살펴보니 timestamp validation 실패가 반복되고 있었습니다. 따라서 적어도 일부 누락은 다음 흐름으로 설명할 수 있었습니다.

```text
metric 생성
    ↓
전송 경로에서 대기
    ↓
REST API 도착
    ↓
timestamp validation 실패
    ↓
저장되지 않음
    ↓
포털의 데이터 밀도 감소
```

실제 허용 범위의 상한과 하한은 이 글에서 확정하지 않습니다. 당시 자료만으로 정확한 validation 조건을 복원할 수 없기 때문입니다. 중요한 것은 특정 임계값을 외워 적용하는 것이 아니라, validation reject가 발생한 요청의 metric timestamp와 receive timestamp를 함께 확인하는 것입니다.

```ts
// 실제 운영 코드가 아닌, 측정해야 할 시간 관계를 보여주는 예시입니다.
const ageMs = receiveTimestamp - metricTimestamp;

if (ageMs > allowedAgeMs) {
  reject('stale metric');
}
```

## 첫 번째 가설: VM 사이 네트워크가 느린가

송신 측과 수신 측은 같은 사내 클라우드 환경의 VM에 있었습니다. 200ms라는 짧은 목표를 두고 있었으므로, 먼저 네트워크 구간에 예상보다 큰 지연이나 불안정성이 있는지 확인했습니다.

송신 측에서 데이터를 보낸 시각과 수신 API가 요청을 받은 시각을 로그로 남기고, 동일 요청을 연결할 수 있는 식별자와 두 timestamp의 차이를 비교했습니다. 측정 결과 네트워크 구간의 지연은 200ms 목표에 비해 작은 수준이었습니다.

이 결과가 네트워크 지연이 전혀 없다는 뜻은 아닙니다. 다만 반복적으로 나타난 1초 수준의 long tail을 네트워크만으로 설명하기는 어려웠습니다. 원인 범위를 애플리케이션 실행 구조와 Telegraf output 처리 쪽으로 좁혔습니다.

<Callout type="tip" title="원인 후보를 한 번에 제거하지 않는다">
  네트워크가 빠르다는 확인만으로 애플리케이션을 원인으로 단정할 수는 없습니다. 구간별 timestamp를
  남기고, 각 변경이 latency 분포의 어느 부분을 바꿨는지 비교해야 다음 실험의 방향을 정할 수
  있습니다.
</Callout>

## 첫 번째 개선: 매번 시작하던 Python을 daemon으로 바꿨다

Python 코드가 metric을 묶고 필드를 가공하는 과정부터 살펴봤지만, 반복되는 지연을 설명할 만한 연산은 찾지 못했습니다. 오히려 200ms마다 처리해야 하는 경로에 Python interpreter와 프로세스를 새로 시작하는 비용이 포함되어 있다는 점이 눈에 띄었습니다.

초기 구조를 단순화하면 다음과 같습니다.

```text
Telegraf collection
    ↓
Python process 생성
    ↓
데이터 가공
    ↓
REST API 전송
    ↓
process 종료
```

이 비용을 경로에서 제거하기 위해 Python sender를 장기 실행되는 daemon 형태로 변경했습니다. Linux 서비스로 등록해 OS 재부팅 이후에도 다시 기동되도록 했고, 실제 재부팅 과정에서 자동 기동 여부를 확인했습니다.

### script 실행과 daemon의 trade-off

요청마다 프로세스를 실행하는 방식은 실행이 끝나면 생명주기가 자연스럽게 끝난다는 장점이 있습니다. 반면 짧은 주기마다 interpreter와 프로세스를 초기화해야 합니다. daemon은 이 반복 비용을 없애지만, 비정상 종료와 재기동, 장기 실행 중 메모리 사용량을 별도로 관리해야 합니다.

| 방식                 | 장점                                    | 부담                                            |
| -------------------- | --------------------------------------- | ----------------------------------------------- |
| 요청마다 Python 실행 | 장기 실행 프로세스를 관리하지 않아도 됨 | 짧은 주기마다 프로세스 시작 비용 발생           |
| Python daemon        | 반복적인 프로세스 시작 비용 제거        | 재기동, 서비스 상태, 장기 실행 안정성 관리 필요 |

daemon 적용 후 전송 지연은 줄었습니다. 다만 daemon이 장기간 실행되는 동안 메모리 사용량이 안정적이었다고 정량적으로 주장할 자료는 남아 있지 않았습니다. 이 방식으로 운영한다면 process memory, restart count, sender error rate를 별도 운영 지표로 두는 편이 안전합니다.

## daemon 이후에도 남은 1초대 long tail

daemon 적용 후의 변화는 첫 번째 가설이 일부 맞았음을 보여주었습니다. 하지만 측정 결과 p95와 p99에는 여전히 1초를 넘는 요청이 존재했습니다. 즉 Python process 생성 비용을 제거한 것만으로는 200ms 목표를 만족하지 못했습니다.

여기서 daemon화를 곧바로 최종 해결책으로 판단하지 않은 것이 중요합니다. 네트워크 구간의 지연은 주된 원인으로 보기 어려웠고, Python의 반복 실행 비용도 줄였지만, 파이프라인 어딘가에 1초 단위로 대기하는 요소가 남아 있었습니다.

## 두 번째 개선: collection interval과 flush interval을 분리했다

Telegraf에는 메트릭을 수집하는 주기와 수집한 metric을 output으로 내보내는 flush 주기가 따로 있습니다. 따라서 collection interval을 200ms로 설정해도 수집 직후 외부 API로 전송된다는 보장은 없습니다.

당시 flush interval은 약 1초 수준으로 설정되어 있었습니다. Python sender를 daemon으로 바꿔도 Telegraf가 output을 flush하기를 기다리는 시간이 남아 있었던 것입니다.

처음에는 요구사항과 같은 200ms로 flush interval을 맞추면 충분할 것이라고 예상했습니다. 그러나 실제 측정에서는 200ms 설정만으로 p95와 p99가 목표 범위에 안정적으로 들어오지 않았습니다. 설정값과 end-to-end latency가 같지 않다는 사실을 확인한 뒤, flush interval을 단계적으로 줄이며 수신 지연 분포를 반복 측정했습니다.

```text
기존: 약 1s
  ↓
200ms
  ↓
100ms
  ↓
약 50ms 수준
```

약 50ms 수준까지 조정했을 때 p95와 p99가 모두 목표인 200ms 안으로 들어오는 것을 확인했습니다. 여기서 `flush_interval=200ms`이면 지연이 정확히 400ms가 된다고 해석하지 않았습니다. 실제 end-to-end latency에는 수집 타이밍, flush 타이밍, sender 처리, 네트워크, API validation 전후의 시간이 함께 포함되기 때문입니다.

<Callout type="warning" title="flush를 줄이면 비용도 측정해야 한다">
  flush interval을 낮추면 output 처리 빈도가 늘어날 수 있습니다. 이번 작업에서는 latency 목표 충족
  여부를 확인했지만, CPU 사용량과 network I/O가 얼마나 증가했는지는 별도로 정량화하지 못했습니다.
  운영 환경에 적용할 때는 latency와 함께 flush 횟수, CPU, network I/O를 확인해야 합니다.
</Callout>

## 변경 후 구조와 측정 기준

최종적으로는 Telegraf의 flush 대기 시간을 줄이고, Python sender를 상시 실행하는 구조로 바꿨습니다.

<Mermaid chart={changedFlow} label="Improved metric delivery flow">
  <span slot="caption">
    flush 대기와 매 수집마다 발생하던 프로세스 시작 비용을 각각 줄인 뒤 API 수신 지연으로 효과를
    확인했습니다.
  </span>
</Mermaid>

관찰한 변화는 다음과 같이 정리할 수 있습니다.

| 단계                       | 확인한 결과                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| 최초 구조                  | 일부 요청이 timestamp validation에서 거절되었고, 포털에 데이터가 부족하거나 없는 초가 발생 |
| 네트워크 확인              | 200ms 목표에 비해 작은 수준으로, 반복되는 1초대 지연의 주된 원인으로 보기 어려움           |
| Python daemon 적용         | 전송 지연 감소. 그러나 p95와 p99에 1초 이상 구간이 남음                                    |
| flush interval 단계적 축소 | 약 50ms 수준에서 p95와 p99가 모두 200ms 이내로 들어옴                                      |

이 글에서 확정할 수 있는 수치는 “약 50ms 수준으로 조정했을 때 p95/p99가 200ms 안으로 들어왔다”는 관찰입니다. 각 단계의 정확한 p50, p95, p99, validation reject 비율, 초당 저장 point 수는 당시 로그와 설정 이력을 다시 확인하기 전까지 제시하지 않습니다.

지연을 재현하거나 다른 시스템에 적용할 때는 하나의 평균값만 기록하지 말고, 적어도 다음 관계를 같은 요청 단위로 남기는 것이 좋습니다.

```ts
type MetricTiming = {
  metricTimestamp: number;
  flushTimestamp: number;
  senderTimestamp: number;
  receiveTimestamp: number;
};

const endToEndMs = timing.receiveTimestamp - timing.metricTimestamp;
```

평균값은 일부 긴 지연을 숨길 수 있습니다. 이 사례처럼 validation reject와 포털 누락이 문제라면 p95와 p99를 함께 보고, 변경 전후 reject 건수와 실제로 저장된 point 수까지 연결해야 개선이 사용자 화면에 반영되었는지 확인할 수 있습니다.

## 대안 비교: Telegraf에서 API를 직접 호출할 수 있었을까

지연만 보면 Python 계층을 제거하고 Telegraf가 REST API를 직접 호출하는 선택지도 있습니다. Python process 생성 비용을 없애고 경로를 짧게 만들 수 있기 때문입니다.

하지만 당시에는 같은 timestamp에 수집된 여러 metric을 하나의 의미 있는 단위로 묶고, 일부 필드를 가공해야 했습니다. 이 책임을 Telegraf 설정만으로 처리하기보다 Python에서 명시적으로 다루는 편이 구현과 유지보수에 유리하다고 판단했습니다. 그래서 개선 과정에서도 Python 계층 자체를 없애지 않고, 반복 실행 비용을 daemon으로 제거했습니다.

| 선택                      | 기대 효과                      | 당시 판단                                                            |
| ------------------------- | ------------------------------ | -------------------------------------------------------------------- |
| Telegraf → API 직접 전송  | Python 실행 경로 제거          | timestamp 기준 묶음과 필드 가공을 구성하기 불편해 초기 설계에서 제외 |
| 기존 Python script 최적화 | Python 내부 연산 비용 감소     | 코드 검토 결과 반복되는 1초대 지연을 설명하기 어려움                 |
| Python daemon             | 프로세스 시작 비용 제거        | 적용. 대신 서비스 생명주기 관리 필요                                 |
| flush interval 축소       | Telegraf 내부 output 대기 감소 | daemon 적용 후 남은 long tail을 줄이기 위해 단계적으로 적용          |

## 결과와 남은 trade-off

이 문제는 하나의 병목으로 설명되지 않았습니다. 변경 전 경로에는 적어도 Telegraf output flush를 기다리는 시간과 매 수집마다 Python process를 시작하는 시간이 함께 존재했습니다.

daemon으로 변경했을 때 latency가 줄었다는 점에서 프로세스 시작 비용이 실제 경로에 영향을 주고 있음을 확인했습니다. 그러나 그 변경만으로 p95와 p99가 200ms 안에 들어오지는 않았습니다. 이후 flush interval을 약 50ms 수준까지 낮춘 뒤에야 p95와 p99가 목표 범위 안으로 들어왔습니다.

이 사례에서 얻은 결론은 다음과 같습니다.

1. `collection interval`은 데이터 생성 주기이지, API 도착 주기가 아닙니다.
2. 짧은 주기의 파이프라인에서는 프로세스 생명주기 비용도 end-to-end latency의 일부입니다.
3. 평균 latency만으로는 long tail과 timestamp validation reject를 설명할 수 없습니다.
4. 병목을 하나씩 분리해 변경하고, 각 단계의 p95/p99와 reject 결과를 함께 확인해야 합니다.

<Callout type="note" title="측정되지 않은 비용을 결과로 포장하지 않는다">
  약 50ms 수준의 flush 조정으로 p95와 p99가 200ms 안에 들어왔다는 것은 확인했지만, 그 조정이 CPU와
  network I/O에 미친 영향은 이 자료만으로 확정할 수 없습니다. daemon의 장기 메모리 안정성도 별도
  시계열 측정이 필요합니다.
</Callout>

## 마치며

`collection_interval=200ms`는 요구사항의 시작점일 뿐이었습니다. 실제 데이터 경로에는 Telegraf의 flush 대기, Python process 시작, 네트워크 전송, 서버 validation이 차례로 존재했습니다. 수집 주기만 보고서는 포털에 데이터가 어느 속도로 도착하는지 알 수 없었습니다.

그래서 검증 기준을 설정값에서 end-to-end latency로 옮겼습니다. 수신 로그의 timestamp validation 실패를 출발점으로 네트워크 구간을 확인하고, Python 실행 구조와 Telegraf flush를 순서대로 분리해 변경했습니다. 첫 번째 변경으로 목표를 만족하지 못했기 때문에 두 번째 병목까지 찾을 수 있었습니다.

비슷한 문제를 만났다면 먼저 “수집 주기가 짧은가?”보다 “metric timestamp가 API에 도착하고 저장되기까지 어디에서 기다리는가?”를 질문하는 것부터 시작하면 됩니다.
